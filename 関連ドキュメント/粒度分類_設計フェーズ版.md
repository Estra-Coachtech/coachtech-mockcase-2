## 2. 勤怠に固有の事情 ─ 提供 Blade が確定させている契約

Bookshelf と同じく、**配布物がすでに答えを固定している範囲**があります。勤怠はここが Bookshelf より広く、
**「真に受講生が決める名前空間」はテーブル名だけ**でした。これを確認せずに要件シートから識別子を抜くと、
「自分で設計してください」と書いた要件シートと、答えを固定している提供 Blade が食い違うという
Bookshelf で起きた不整合をそのまま持ち込むことになります。

出どころは `coachtech-prepared-file/Preparedblade-mockcase-Attendance`（`basic` / `advanced`）です。
本リポジトリの `resources/views/` と一致することを diff で確認しました（差分は `advanced` 由来の `reports/` のみ）。

### 2-1. モデルの属性名（Blade が直接読む）

| Blade | 参照 | 意味 |
|---|---|---|
| `admin-attendance-list` | `$attendanceRecords->where('user_id', …)` | 勤怠レコードの所有者を指す**外部キー名が `user_id`** に固定される |
| `admin-attendance-list` | `$attendance->clock_in` / `clock_out` / `total_time` / `total_break_time` | 勤怠レコードが**この4つの名前で値を返す**こと（カラムでもアクセサでもよい） |
| `admin-application-detail` | `$application->application_date` / `approval_status` / `comment` / `new_clock_in` / `new_clock_out` / `new_date` | 修正申請が**この6つの名前で値を返す**こと |
| `admin-detail` / `user-detail` | `$break['break_in']` / `$break['break_out']` | 休憩が**この2つの名前で値を返す**こと |
| `layouts/admin-app` | `Auth::user()->admin_status` | 管理者かどうかを表す**属性名が `admin_status`** に固定される |
| `attendance-register` | `$user->attendance_status` | 打刻ステータスを表す**属性名が `attendance_status`** に固定される |
| `staff-list` | `$user->name` / `$user->email` / `$user->id` | ─ |

### 2-2. リレーション名

`$application->AttendanceRecord`（修正申請 → 勤怠レコード）、`$application->proposalBreaks`（修正申請 → 申請中の休憩）、
`$application->user` の3つが Blade に**モデルのプロパティとして**書かれており、**リレーションメソッド名が固定**されます
（PHP のメソッド名は大文字小文字を区別しないので、`attendanceRecord()` と定義しても `$application->AttendanceRecord` で解決されます）。

> ⚠️ `$attendanceRecord['breaks']`（`admin-detail`）と `$data['breaks']`（`user-detail`）は**コントローラがビューに渡す配列のキー**です
> （`admin-detail` 側は `isset()` と `is_array()` で守られています）。リレーション名までは固定しませんが、**キー名 `breaks` は固定**されます。

### 2-3. 状態を表す値

**Bookshelf の Enum backing value にあたるものが、勤怠では Blade に日本語リテラルで直接書かれています。**

| 対象 | 値 | 出どころ |
|---|---|---|
| 打刻ステータス | `勤務外` / `出勤中` / `休憩中` / `退勤済` | `user/attendance-register.blade.php` の `@if($user->attendance_status === '勤務外')` ほか |
| 申請の承認状態 | `承認待ち` / `承認済み` | `user-application-list` / `admin-application-list` / `admin-application-detail` の `===` 比較 |

→ **勤怠には「Enum の値の宣言解決」が要りません。** Bookshelf で必要だった `EnumCaseResolver` 相当の機構は、
このスイートでは出番がありません（→ §7 の申し送り）。

### 2-4. リクエストのキー名

打刻の `action`（`clock_in` / `clock_out` / `break_in` / `break_out`）、修正申請の `new_date` / `new_clock_in` /
`new_clock_out` / `new_break_in[]` / `new_break_out[]` / `comment`、認証の `name` / `email` / `password` /
`password_confirmation`、絞り込みの `user_id` / `year_month` / `date` / `tab_item` が Blade の
`name="…"` と `@error('…')` に書かれており、**リクエストキーとバリデーションキーが固定**されます。

### 2-5. URL

Blade の `action` / `href` に `/attendance`・`/attendance/list`・`/attendance/{id}`・`/attendance/report`・
`/stamp_correction_request/list`・`/stamp_correction_request/approve/{id}`・`/admin/login`・`/admin/attendance/list`・
`/admin/staff/list`・`/admin/attendance/staff/{id}`・`/export`・`/login`・`/logout`・`/register` が直書きされています。

> ⚠️ **要件シート「画面設計」タブの `/attendance/detail/{id}`・`admin/attendance/{id}` は古い記述です。**
> 提供 Blade と模範解答はどちらも `/attendance/{id}`（一般・管理者で共有し middleware で分岐）です。
> 既知の不整合として `suites/attendance/design-notes.md` §6 に記録があり、**設計フェーズ版では提供 Blade 側に揃えます。**

### 2-6. 画面に描かれる文言

**提供 Blade が直接書いている文言があります。受講生の実装では決まりません。**

| 文言 | 出どころ | 現行の要件シート・評価シートの記述 |
|---|---|---|
| `お疲れ様でした。` | `user/attendance-register.blade.php:31` | 一致（FN022） |
| `承認待ちのため修正できません` | `user/user-detail.blade.php:159` | ⚠️ **食い違い。** 要件・評価シートは「**承認待ちのため修正はできません。**」（「は」と句点あり） |

> ⚠️ 後者は**受講生が触らない Blade の中身**なので、文言の差を受講生の実装の欠陥として扱えません。
> 100%版に採点者向けの注意として明記しました。**50%版では「提供 Blade が描画します」と添えて開示**しています
> （隠しても受講生の手元の Blade に書いてあるため、隠すこと自体が成立しません）。

### 2-7. 真に受講生が決めるもの

| 対象 | 例（模範解答の場合・**正解ではない**） | 解決源 |
|---|---|---|
| **テーブル名** | `attendance_records` / `applications` / `breaks` / `application_breaks` | migration の列の組・Model の `$table`／クラス名の規約形 |
| **クラス構成** | どのコントローラに何を置くか・サービスに切り出すか | ─（採点しない） |
| **`total_time` / `total_break_time` の持ち方** | カラムとして持つか、アクセサで計算するか | ─（採点しない。Blade がその名前で読めればよい） |
| **バリデーションの記法** | `required\|date_format:H:i` の書き方 | ─（採点しない。弾く条件と文言だけが要件） |
| **テストケースの中身** | ─ | ─（採点しない。対象カテゴリだけが要件） |

### 2-8. 50%版の例文に使ってよい値

方針書 §5-2 は「ヒアリング例文は**問いの形だけ残して値を抜く**」としています。運用上の規則として、次を守ってください。

> **シート2 のヒアリング例文には、50%版が既に開示している値しか使わない。**

初稿では例文が「休憩は1日に何回でも」「残業は1日8時間を超えた分」「エラーの文言は『備考を記入してください』」を
そのまま載せており、**50%版の本文で伏せている値を例文が漏らしていました**。開示検査は「100% − 配布版」の差分で
許可語彙を作るので、伏せた値が配布版のどこかに載っていると、その項目はヒアリング対象として成立しません。
現在の例文は、勤怠一覧の初期表示月（FN024）・打刻ステータスの値（シート5-1）・休憩戻の遷移先（FN021）・
管理者修正の反映（FN040）・残業の定義（シート5-3）だけを使っています。

なお **マイ勤怠レポートのしきい値（8時間 / 9:00 / 18:00 / 10時間）は開示側に倒しました。**
シート7（初期データ）が採点用の意図的データとして「遅刻（9:30-18:00）2件」「総残業時間 10 時間」等を
配布版にも載せる必要があり、伏せる側に倒すと同じ資料の中で矛盾するためです。

## 8. ハーネス側への申し送り（本リポジトリでは触らない）

Issue #6 のとおり判定機構は課題非依存で `orchestrator/` に実装済みです（[harness#273](https://github.com/estra-inc/lms-grading-harness/pull/273)）。
横展開の1本目として勤怠に当ててみて分かったことを、[harness#270](https://github.com/estra-inc/lms-grading-harness/issues/270) Phase 5 向けに書き残します。

### 8-1. `DesignDocsGate` は `stateDiagram` を検証できない

`orchestrator/Static/DesignDocsGate.php` の `validateMermaid()` は、型が `erdiagram` でなければ
**すべて `validateFlowchart()` に落ちます**。`validateFlowchart()` は先頭行に `^(?:flowchart|graph)\b` を要求するので、
`diagrams:` に `type: stateDiagram` を宣言すると**必ず FALSE になります**（理由文は「先頭行が flowchart でない」）。

勤怠は 勤務外 → 出勤中 ⇄ 休憩中 → 退勤済 と、修正申請の 承認待ち → 承認済み という**状態遷移が課題の中核**で、
教材 Tutorial 16（16-1-5）も `behavior.md` を `stateDiagram-v2` と `sequenceDiagram` で教えています。

**設計フェーズ版は `behavior.md` を提出物に含めますが、図ゲートは掛けません**（見出しの存在と配下の非空だけを見る）。
ハーネスを改修せずに済ませるための措置で、`stateDiagram` / `sequenceDiagram` への対応は Phase 5 の課題として残します。

### 8-2. Enum の宣言解決は勤怠では使わない

§2-3 のとおり、状態を表す値は提供 Blade に日本語リテラルで直接書かれています。
`EnumCaseResolver` の出番はありません。**勤怠で宣言解決が要るのはテーブル名だけ**で、
そのテーブル名も §5-1 の書き換えで API の3行からは消えるため、残るのは
「テーブル名はスネークケース・複数形か」（`AT-DB-05`・実値に依存しない CONV）だけになります。

> つまり勤怠は、**Phase 2 の機構をほとんど使わずに成立します。**
> 「設定を差すだけで済むか」の検証としては、機構が要らない側の実例にあたります。

### 8-3. 新しい `exam_slug` が要る

方針書 §6-7 のとおり、`sheet-map` が行番号で結線しているため、**行構成の違う版を1つの map で扱えません。**
現行 `suites/attendance/` は `legacy` / `current` の2バリアントを既に持っていますが、
設計フェーズ版は**3つめのバリアントではなく別スイート**として立てる必要があります。
